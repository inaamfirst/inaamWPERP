# Repository-Wide ERP Production Audit

Audit window: 2026-08-21 through 2026-08-23 (Asia/Karachi)  
Authoritative source: repository root; `_release_phase5`, archives, and prior executables were used only for drift/forensic comparison.

## A. Executive Summary

**Production-readiness verdict: Not ready for production launch.**

All reproducible P0 defects and the remediable P1 defects identified in the first audit were repaired and retested. The six missing runtime tables now have a forward migration and readiness checks; the 2,118 orphaned audit references were repaired with a durable deletion policy; web refresh, vendor fulfillment, and binary BFF transport work in a real isolated browser/API stack; the license server now uses transactional database storage; and fresh packages were built from the authoritative root with source/dependency/checksum manifests.

Launch is still blocked by four classes of evidence:

1. AUD-008 remains a P1 product-scope decision: purchasing, suppliers, goods receipt, AP invoices, a real employee domain, and a complete return/refund workflow are absent or incomplete.
2. AUD-009 remains P1 if WhatsApp is sold as a live capability: the repository contains only the local mock adapter.
3. AUD-005 is only partially closed: the new executables are current and hashed, but the repository has no commit history, immutable release tag, formal SBOM, or code signatures.
4. PostgreSQL migration/concurrency, TLS/proxy, SMTP, WooCommerce staging, VAPID delivery, provider integration, restore drills, installer compilation, and production operations were not available for certification.

### Direct answers to the requested investigation

- The original report was a historical baseline. This revision preserves its finding IDs and records the remediation result beside each finding.
- The six tables were missing because revision `62d9d53e1126` returns before executing any DDL and incorrectly says application services create the tables (`migrations/versions/62d9d53e1126_add_ledger_accounts.py:19-23`). Forensic recovery of a stale compiled revision, `e4b6313c83e3`, showed that an autogenerated migration had originally included the six creates mixed with broad unsafe schema churn; that source was replaced by the no-op marker. Tests used ORM `create_all`, so they masked the migration gap.
- The 2,118 records were not production data and not physical SQLite corruption. They were genuine foreign-key defects in a development/demo database: `integrity_check` was `ok`, every violation was `audit_logs.user_id -> users`, all users were demo accounts, and production settings reject SQLite. A pre-reset backup had 357 pseudo-actor orphans; a later demo reset retained audit history while replacing 13 demo users with 8, increasing the count to 2,118.
- No production database, third-party integration, external message, or live store was mutated. The active development SQLite file was snapshotted before each approved remediation migration. Browser and mutating workflow tests used disposable databases.

## G. Migration and Data-Integrity Investigation

### Why the six tables disappeared

The evidence supports a migration-authoring failure rather than SQLAlchemy or SQLite randomly losing tables:

1. ORM models defined all six tables.
2. The compiled cache retained a deleted autogenerated revision (`e4b6313c83e3`) that included their creation together with extensive unrelated drift.
3. The checked-in replacement `62d9d53e1126` deliberately returns at line 23 and claims application services create them; no service does.
4. Tests created schemas from `Base.metadata`, bypassing the Alembic path, so service/API tests passed.
5. Migration `202608210021` now conditionally creates missing tables and adopts already-present ones, preventing duplicate-table failure in installations that were previously bootstrapped from ORM metadata.
6. Readiness and preflight now require all six objects, so revision equality alone cannot produce a healthy result.

### Classification of the 2,118 violations

| Evidence | Finding |
|---|---|
| `.env` and settings | Development SQLite; production validation requires PostgreSQL. |
| User identities | Only demo/local users such as admin, vendor, manager, and rider accounts; no production population evidence. |
| `PRAGMA integrity_check` | `ok` before and after remediation: no physical page/index corruption. |
| `PRAGMA foreign_key_check` before | 2,118 rows, all `audit_logs.user_id -> users`. |
| Older pre-reset backup | 357 audit rows referenced the literal pseudo-actor `system`. |
| Reset behavior | Audit rows were retained while demo users were deleted/recreated, expanding orphan count to 2,118. |
| Other consistency queries | No duplicate key groups, cross-tenant joins, negative money/stock groups, overpayments, unbalanced posted journals, outbox/inbox duplicates, or multiple active sync-run keys. |

Therefore the database was a logically inconsistent development/demo copy, not a production database and not a physically corrupted SQLite file. The defects were still real and required repair because they invalidated audit attribution and could be recreated by reset/seed.

### Repair and current state

- Migration `202608210022` nulls orphan actor IDs and recreates the audit-user FK with `ON DELETE SET NULL`.
- ORM deletion behavior matches the migration.
- Reset/seed nulls audit actors before deleting demo users and asserts `foreign_key_check` in its test.
- Background pseudo-actor fallbacks no longer insert the invalid literal `system`; conflict resolution records the authenticated user (`erp/packages/core/api/routes.py:2666-2684`).
- The active dev database was consistently snapshotted before migration. Current state: revision `202608210023`, integrity `ok`, zero FK violations, zero audit orphans.

### Remaining schema risk

`alembic check` still reports substantial historic index/constraint/type/nullability drift. SQLite autogeneration accounts for some naming noise, but the operations have not been individually adjudicated on PostgreSQL. This is P2 debt and a staging gate, even though the direct missing-table P0 is closed.
